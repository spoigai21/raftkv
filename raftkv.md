# raftkv — Goals

What this project is, why it exists, and what counts as done.
The step-by-step build is in `raftkv-implementation.md`.

**Status:** complete. The demo is a recorded run in the README, in place of a video.

---

## 1. In one paragraph

Build a replicated key–value store in **C++20** on top of the **Raft** consensus algorithm:
three or five independent processes that agree on an ordered log of operations, survive the
loss of a minority of nodes, recover their state from disk after a crash, and never lose a
write they acknowledged. Then — and this is the actual point — **prove** those properties
with a deterministic simulator, a matrix of injected failures, and a linearizability checker
run over recorded histories.

## 2. What we are trying to do

### The primary goal

Produce one artifact that answers the question infra teams actually screen for:
**"what happens to your system when part of it dies?"**

Everything currently on the résumé — Adorus, HerbsPro, Countera, swing, CineInfer — runs on
a single machine. They demonstrate product engineering, data handling, and measurement
discipline. None of them can answer that question, and it is the question behind Qumulo's
"fault-tolerant block layer", Databricks' "platform that scales", and Cisco's "distributed
architectures".

### The secondary goal

Convert "has written C++" into "writes systems C++". The record already has CUDA kernels
(2,818 lines), a Qt desktop app, ~1,948 lines of algorithm solutions, and a year of TA'ing
C++ labs. What it lacks is C++20 in a real systems context: toolchain discipline (CMake
presets, vcpkg), concurrency outside GPU kernels, and memory-safety evidence
(ASan/UBSan/TSan, fuzzing). C++ appears in **22 of the 65 saved JDs** — more than Go (15)
or Rust (5) — so this is the higher-frequency gap, and it compounds with the CUDA work
instead of starting a new thread.

### What we are explicitly *not* trying to do

- Not trying to be fast. Throughput numbers from a laptop impress nobody, and claiming
  otherwise damages credibility.
- Not trying to be a database. No transactions, no indexes, no query language.
- Not trying to beat etcd or Consul. This is a learning artifact with honest evidence.
- Not trying to look bigger than it is. The README states the scope limits in the first
  three sentences.

## 3. Why Raft specifically

- It is the **canonical** distributed-systems artifact: an interviewer knows immediately
  what you did and how hard it is.
- The paper is a specification you can implement literally, so the failure mode is "I
  misread Figure 2", not "I invented something unverifiable".
- Its correctness conditions are **checkable**: linearizability is a property a tool can
  verify over a recorded history, which turns the project from a demo into evidence.
- The failure scenarios are dramatic and easy to show on camera — kill the leader, watch the
  cluster elect a new one and keep its promises.

## 4. What success looks like

The project is done when a reader who spends four minutes on the README can see all of this:

| Claim | The evidence for it | Where it stands |
|---|---|---|
| It really replicates | 100 entries proposed at the leader appear in identical order on every node | ✓ `RaftReplication.HundredEntries…`, 20 seeds |
| It survives leader loss | leader killed mid-write; new leader elected; **no acknowledged write lost** | ✓ fault matrix row 1 (simulator), `tools/demo.sh` (real processes, Porcupine-checked) |
| It fails safely, not wrongly | majority partition → refuses writes (unavailable, not inconsistent) | ✓ `FaultMatrix.MajorityPartition`: nothing commits, history linearizable |
| It recovers | `kill -9` all nodes, restart, committed prefix unchanged | ✓ simulator on real files, and `tests/cluster/smoke.sh` with real processes |
| It stays correct under chaos | 100 seeded runs with drops, delays, reorders and partitions pass a linearizability checker | ✓ 540 histories (about 297k operations), plus a real-process one |
| It is memory- and thread-safe | ASan/UBSan/TSan clean in CI; the log decoder fuzzed | ✓ every push, with a hardened standard library; fuzzed 60 s per push |
| It is reproducible | every failure replays from `--seed N` | ✓ `RAFTKV_SEED=N`; golden tests check macOS and Linux agree |
| It is measured, not asserted | `docs/results.csv` generated by code; the README reads from it | ✓ CI fails if the README and the CSV disagree |

Anything that cannot be demonstrated this way does not go in the README.

## 5. Scope

**In scope**

- Leader election, log replication, persistence, crash recovery, snapshots and compaction
- A KV state machine (`Get`/`Put`/`Append`) with duplicate-request detection
- A deterministic simulator: virtual clock, seeded network, injectable faults
- A fault matrix as automated tests, a linearizability checker, and benchmarks
- A written postmortem of every real bug found, in the style of swing's 54 postmortems

**Out of scope for v1** (candidates for later, in this order)

1. Membership changes (adding/removing nodes)
2. `ReadIndex` or lease-based reads
3. A gRPC front end
4. Multi-Raft sharding across groups

## 7. Predictions to commit before measuring

Written down and committed to git *before* Phase 9, then confirmed or refuted in the
write-up — the same honesty structure as swing and CineInfer.

Committed on 2026-10-03, after the benchmark tooling (`f5de2d4`) and before any measurement.
Setup: 3 or 5 `raftkvd` processes on this laptop, 32 closed-loop clients, durable fsync.

1. Write throughput drops **about 25%** going from 3 nodes to 5.
2. Recovery after `kill -9` of the leader completes in **under 1000 ms**.
3. Batching up to 64 entries per `AppendEntries` improves throughput by **about 2×** over one
   entry per RPC.
4. *(Not a prediction; already measured.)* A 20% message-drop rate costs less than ___%
   throughput. Phase 7's fault matrix measured it before this list was filled in: in the
   simulator, 20% drops kept **5.2%** of normal throughput, i.e. cost about 95%.
5. *(Not a prediction; unresolved so far.)* The linearizability checker finds at least one
   real bug that the unit tests missed. **So far it has not.** Of the two real bugs found:
   the invariant checker found postmortem 001, a bug in the checker itself; the repeated
   real-process test found postmortem 002, in the transport. The checker has caught every
   planted bug.

Prediction 5 is the interesting one: if it is wrong, that is a result worth reporting too.

**Measured** (Phase 9, `docs/results.csv`; the full table is in the README):

1. ✗ 3 → 5 nodes cost **7.3%**, not 25%. Each node is bound by its own fsync, and followers
   sync in parallel with each other, so extra followers cost little.
2. ✓ Writes resumed **495 ms** (median) and **503 ms** (worst of 5) after `kill -9` of the
   leader. That figure is set by the client's 500 ms request timeout, not by the election.
3. ✗ Batching gave **3.4×**, not 2×. With one entry per RPC, followers also sync once per
   entry, and replication takes a round trip per entry.

These scores stand against the version the predictions were made about. Phase 9's
measurements are frozen in `docs/results-phase9.csv`. Three later improvements (group
commit, an adaptive client timeout, PreVote/CheckQuorum) changed the numbers since; the
before and after are in `docs/results.md`.

## 8. Risks, and what to do about them

| Risk | Mitigation |
|---|---|
| Raft's edge cases eat weeks | Follow Figure 2 literally; build the simulator first so bugs replay from a seed |
| C++ tooling drag (vcpkg, CMake) | Phase 0 exists solely to get this working before any logic is written |
| macOS toolchain differs from Linux CI | Apple clang has no libFuzzer, so fuzzing runs in CI or with Homebrew `llvm`; `jthread` needs the macOS 26 SDK; a golden event-log test catches seed replays that differ between libc++ and libstdc++ |
| Debugging concurrency by print statement | Single-threaded Raft core driven by a deterministic event loop, plus TSan on the real node; never `steady_clock::now()` or `std::` random distributions in Raft code |
| A design choice forces a rewrite at Phase 4 or 8 | Threading model, injected `Env`, storage interface and index conventions are fixed up front (implementation guide §3) |
| Silent correctness bugs | The linearizability checker is the backstop; unit tests alone will not find these |
| Scope creep into sharding/membership | Explicitly deferred in §5; v1 ends at one Raft group |
| It never gets finished | Phase 7 is the honest stopping point — ship the write-up there if time runs out |

## 9. Cost

**$0.** Every component is free and runs on the laptop:

| Component | License / cost |
|---|---|
| gcc / clang, CMake, Ninja | free, open source |
| vcpkg | MIT |
| standalone Asio | Boost Software License |
| Protocol Buffers | BSD |
| GoogleTest / Google Benchmark | BSD / Apache 2.0 |
| nlohmann/json | MIT |
| ASan / UBSan / TSan / libFuzzer | part of clang, free |
| Porcupine (linearizability checker) + Go toolchain to run it | MIT / BSD |
| tl::expected | CC0 |
| GitHub Actions | free tier covers public repos |
| The "cluster" | 3–5 processes on your own machine |

No cloud account, no GPU rental, no paid services. The only two caveats worth knowing:
**Docker Desktop** has licensing terms for large companies — irrelevant for personal use,
and Colima or Podman are free alternatives if you ever need one. And if you later decide to
run nodes on separate cloud VMs, that is optional and adds nothing to the evidence, since
every interesting failure is easier to *cause* locally.

The real cost is time: **5–7 weeks part-time** to a demoable Phase 8 in C++20 (3–4 in Go —
see the appendix of the implementation guide).
